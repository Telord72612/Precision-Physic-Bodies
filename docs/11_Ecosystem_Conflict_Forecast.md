## TIER 1 — CRITICAL / HIGH (fix or formally accept before shipping)

### HIGGS binary coupling [17A-1] — CRITICAL, gate
PPB calls HIGGS vtable slots 0–40 with **no version gate**. Slot 33 (AddPostVrikPostHiggsCallback)
CTDs on older HIGGS builds; any vtable shift misroutes every callback. Prevention: minimum-build-number
gate + known-good allowlist, SEH-probe the registrations (FsmpLink::ReadVersion pattern already exists
in-repo), loud log on refusal.

### 0xB266AB chain order [17A-2] — HIGH, process
The pre-drive hook chain (PPB / collviz / AIHands / PLANCK) depends on install timing + DLL-name load
order. A PLANCK update or a third mod hooking the same site can silently unchain us. Prevention:
per-PLANCK-update checklist (re-read the rel32 at the site), document the DLL-name ordering invariant.

### 8 PLANCK behavior dependencies [17A-3] — HIGH, process
PD-drive, postPhysics write-back, node write-back orbit assumption, foot-IK memcpy order, constraint
recreation (PivDescale pointer keys), KEYFRAMED_REPORTING discriminator, 56×biped Continue, wfm scale
flattening. Each has a break scenario in 17A. Prevention: this list IS the PLANCK-update source-diff
gate — diff these 8 behaviors on every PLANCK release before updating (the 0.7.1→0.8.0 diff already
followed this pattern and passed).

### DisableAI'd standing NPCs poison calibration [17A-4] — HIGH, flag
PLANCK 0.8.0 loosens ragdolls of DisableAI'd NPCs (paralysis/capture/down-state mods do this
constantly in this load order) while ActorRagdollAttached still reads "attached" → samplers latch
poisoned rootDelta/headTrim/effScale. Same disease as the furniture poisoning the user diagnosed.
Prevention: add the AI-disabled check to the gate.

### Get-up / knockdown frames invisible to the gate [17A-20] — HIGH, flag
kGetUp flips IsInRagdollState false → the stood-up edge fires and re-captures **while the body is
still mid-get-up** → poisoned rootDelta. Prevention: `GetKnockState() != kNormal → return false`
(one bitfield read) + ~1s consecutive-attached debounce before samplers open.

### Swimming never gates, never re-measures [17A-21] — HIGH, flag
Swim poses fill whole 10-sample windows with horizontal-body data. Prevention: `IsSwimming() →
return false` (same flags word, free) — water-exit re-measure edge appears automatically.

### Save/load latch leak [17A-30] — HIGH, code (small)
`s_effScale`, `s_applied`, `s_gate` are FormID-keyed statics NEVER cleared on load. Different save /
new game in-session → recycled FormIDs (FF dynamics especially) inherit the previous save's latches.
Prevention: CapFixClearOnLoad() wired into the existing kPreLoadGame Clear* block.

### FSMP bullet-version hole [17A-31] — HIGH, gate
FsmpLink gates only interface MAJOR. An FSMP built on bullet 3.25+ with changed btRigidBody layout
passes the handshake → PreSink writes forces at wrong offsets. Prevention: also require
bulletVersion 3.24 (fields already in VersionInfo, already logged) — one if-statement; census-only
(read) mode on mismatch.

### skeleton_female.nif is a 5-way loose-file conflict [17A-15] — HIGH, design (small)
MO2 priority is the ONLY thing protecting the bake (PPB line 50 wins today). A VRTouchEvents/SOFTBODY
reinstall or re-sort silently reverts every baked artifact with zero error. Prevention: stamp
`NiStringExtraData PPB_BAKE_vN` into the nif at bake time; PPB.dll probes it on first female ragdoll
attach and logs LOUDLY if absent.

# 17A — Conflict Forecast: FULL FINDINGS (appendix, 2026-07-13)

## [1] [CRITICAL] HIGGS vtable coupling with NO version gate. HiggsInterface.h hand-matches all 41 vfunc slots of IHiggsInterface001 (slots 0-40). PPB actually calls slots 0 (GetBuildNumber), 8 (GetGrabbedObject), 12 (IsDisabled), 16 (IsTwoHanding), 20 (AddCollisionFilterComparisonCallback), 21 (AddPrePhysicsStepCallback), 24 (GetHandRigidBody), 25 (GetWeaponRigidBody), 28 (IsHoldingObject), 33 (AddPostVrikPostHiggsCallback). HandBox.cpp:1352-1355 explicitly DECLINES a GetBuildNumber hard gate ('build->vtable mapping is unpublished... we log the build instead'). GetBuildNumber is logged (Interop.cpp:40) but nothing is gated on it.
**Scenario**: Two directions. (a) HIGGS update that INSERTS or reorders a virtual before slot 33: every call lands one slot off. Pointer-returning polls (GetHandRigidBody/GetWeaponRigidBody) are partially absorbed by IsLikelyPointer + HK_SHAPE_BOX type checks (degrade to no-op), but the three Add*Callback registrations pass a function pointer into the wrong Add — HIGGS later invokes PPB's PrePhysicsStep handler with a comparator signature (or vice versa) on a collision thread: stack/argument mismatch, CTD far from the cause, near-impossible to triage from the log. (b) User runs an OLDER HIGGS whose interface001 vtable is SHORTER than 41 slots (slots 30-40 are late additions): AddPostVrikPostHiggsCallback (slot 33, registered unconditionally in PerfSys::RegisterHiggs and Diag) reads past the real vtable — immediate CTD at kPostPostLoad. Note the interface itself is version-handshaked (GetApiFunction(1) requests revision 001), so historically HIGGS appends only — but that promise covers layout, not length on old builds.
**Prevention**: 1) Minimum-build gate: determine the HIGGS build number where slot 33 first exists (higgsinterface001.h git history) and refuse ALL vfunc-above-19 usage below it, keeping the Interop drift-heuristic fallback path (already exists for HIGGS-absent). 2) Known-good allowlist + one loud log line: on an unrecognized (newer) build, log 'HIGGS build N unverified — hand boxes/slab dial/finger rigs running on an unaudited vtable' so a post-update CTD report is self-diagnosing. 3) SEH-probe the first registration the way FsmpLink::ReadVersion wraps getVersionInfo (FsmpLink.cpp:136-144) — the pattern already exists in this codebase, it just isn't applied to the HIGGS handshake. 4) Cheap runtime sanity: after registration, require the PrePhysicsStep callback to fire with a worldArg that passes IsLikelyPointer within N frames before arming create/destroy.

## [2] [HIGH] 0xB266AB chain-order dependency on PLANCK's INSTALL TIMING, not just its presence. Hooks.cpp:195-232 installs at kDataLoaded specifically because PLANCK Write5Calls the site during its SKSEPlugin_Load; write_call<5> reads the current rel32 (PLANCK's trampoline) as the chained tail. Same pattern at 0xA26C05 (inner drive, PLANCK-contested), 0xB268DC (postPhysics, PLANCK-contested), 0xDFB722 (step, HIGGS-contested). PPB's correctness also depends on being ABOVE PLANCK: ApplyToPoseTrack arms per-drive thread-locals (heel bias, pose-conform TLS) consumed by the inner hook that fires INSIDE the chained driveToPose; the inner-hook conform deliberately postdates PLANCK's foot-IK memcpy of poseLocal over TRACK_POSE. Additionally, chain order among the sibling kDataLoaded chainers (PPB / collviz_markers / AIHands — Hooks.cpp:201 names the full chain) is SKSE messaging-listener order, which follows DLL load order.
**Scenario**: (a) PLANCK 0.9+ moves its hook install from SKSEPlugin_Load to kDataLoaded and its listener runs after PPB's: PLANCK becomes chain head. PPB's pose-conform still applies at the inner hook (below PLANCK's pre-hook), so the pose path survives, BUT the postPhysics compensation ordering flips — ApplyHeelPostFix (Hooks.cpp:242-252) runs after its chained tail assuming PLANCK's write-back already happened; if PLANCK now runs after PPB there, PLANCK re-maps the RAISED ragdoll over PPB's compensated root → every heeled NPC's rendered body floats ~8u. (b) Any third mod that PATCHES 0xB266AB without chaining (raw byte write instead of write_call) silently orphans PPB's hook — heel/CapFix/PivFix/statue/LOD pipeline all go dead with zero log evidence beyond the missing FIRST-FIRE line. (c) Renaming any sibling DLL (PPB.dll vs collviz_markers.dll vs AIHands.dll) reorders the chain — the inner-hook TLS handoff only tolerates reordering among mods that don't touch the same tracks.
**Prevention**: 1) Per-update PLANCK checklist (extend the 0.7.1→0.8.0 verdict method): re-verify install SITE (still 0xB266AB/0xA26C05/0xB268DC), install TIME (still SKSEPlugin_Load), and pre-vs-post placement of the foot-IK memcpy and the node write-back. 2) Add a save-load-time site audit: re-read the 5 bytes at 0xB266AB and confirm the rel32 still targets PreDriveChainHook; if not, log 'PPB was UNCHAINED by a later patcher' loudly. The FIRST-FIRE module-resolve + ChainVerdict logging (Hooks.cpp:137-147) is already excellent — this closes the remaining silent-death case. 3) Document the DLL-name ordering invariant in the module report so a future rename is caught at review.

## [3] [HIGH] PLANCK BEHAVIORS PPB silently depends on (the concrete re-verify list per PLANCK update): (1) PD-motor drive of ragdoll bodies toward worldFromModel × pose — heel fix v3 (PPBHook.cpp:117-155) and the XP32 pose-conform both bias TARGETS and rely on PLANCK/engine motors doing the actuation; (2) postPhysics writes the ragdoll back into the output pose with the UNBIASED transform — heel v4 compensation (ApplyHeelPostFix) subtracts heelZ from the root AFTER downstream; (3) PLANCK writes the risen ragdoll into scene-graph nodes — the pose-conform root delta is a CONSTANT captured once per ragdoll build precisely because live-node targeting fed back into orbit (PPBHook.cpp:387-390); (4) foot-IK memcpy of poseLocal over TRACK_POSE happens in PLANCK's PRE hook — PPB's conform applies at the INNER hook so it survives; (5) hinge→ragdoll constraint conversion creates NEW hkpConstraintInstance objects — PivDescaleApply (PivFix.cpp:657-689) keys 'already descaled' on instance POINTER identity and relies on rebuilds producing fresh instances carrying freshly-scaled pivots; (6) PLANCK upgrades HIGGS bodies to KEYFRAMED_REPORTING and branches on it — PPB's boxes use plain KEYFRAMED to stay OUT of PLANCK's hit/damage/aggro paths (HandBox.cpp:816-818); (7) PLANCK's own HIGGS comparator callback Continues for layer-56 × biped (HandBox.cpp:1407); (8) the engine/PLANCK flattens worldFromModel scale before the inner controller — PPB sources actor scale from the WORLD_FROM_MODEL track instead of the param (PPBHook.cpp:660-673).
**Scenario**: Each has a distinct break: (1) gain changes → heel-raised ragdoll lags/overshoots (degrade, visible). (3) If PLANCK 0.9 stops or changes node write-back, the once-captured root delta baked the OLD feedback assumption — conform roots drift by the old compensation amount on every NPC (systematic ~constant error, wrongly diagnosed as skeleton data). (5) If PLANCK ever RE-STAMPS pivot translations on an EXISTING instance (instead of recreating), PivDescale's pointer key says 'already done' and skips → scaled actors regress to squashed pivots; conversely if PPB's descaled instance gets re-scaled in place, values are now double-wrong. (6) If PLANCK changes its discriminator from quality-type to layer-56 membership, PPB's hand boxes suddenly generate hit/damage/aggro on every flesh push — NPCs turn hostile from a graze. (7) If PLANCK's comparator stops Continuing for 56×biped and returns Collide/Ignore first, PPB's entire FilterDecision splice is preempted (see comparator finding).
**Prevention**: Codify this list as the PLANCK-update gate in Report/Precision Physic Bodies Module (the 0.8.0 verdict proved source-diff is cheap and decisive): diff exactly these 8 behaviors, not 'the hooks are byte-identical'. Items 3 and 5 deserve runtime tripwires: (3) after root-delta latch, keep the existing head-trim sampler but alarm if the 10-sample mean exceeds a sanity bound (it already measures the error — just add the loud log); (5) log when PivDescale sees a NEW instance for a joint whose old instance is still alive (pointer differs but old one not freed is unknowable — instead, periodically re-read one descaled atom and verify the translation still equals the descaled value; mismatch = someone re-stamped it).

## [4] [HIGH] ActorRagdollAttached (PivFix.cpp:707-716) is an ENGINE-STATE PROXY for PLANCK's internal 'loosened' decision: it checks IsInRagdollState + GetSitSleepState + GetOccupiedFurniture and assumes that set exactly matches when PLANCK detaches the ragdoll from the skeleton. Every calibration latch gates on it: measured-scale capsules (CapFix.cpp:527), pose-conform root delta + head trim (PPBHook.cpp:610), and the stand-up edge triggers re-capture. But the PLANCK 0.8.0 diff already found one divergence: 0.8.0 pulls ragdoll from DisableAI'd NPCs — a state none of the three checks see.
**Scenario**: A quest/scene DisableAI's an NPC (paralysis mods, some capture/down-state mods do this constantly in this load order) while she stands: PLANCK 0.8.0 loosens her ragdoll, PPB's gate still reads 'attached', and the root-delta/head-trim/measured-scale samplers latch garbage from green (detached) bodies. Because the root delta is capture-once-sticky by design, the poisoned constant persists until a furniture edge or reload — the NPC's conformed drive pose is offset by the full detachment error (sky-launch-class symptom the furniture gate was built to prevent, returning through a side door). Any future PLANCK loosening condition (scripted knockdown states, new down-state integrations) widens the same hole.
**Prevention**: 1) Add the known 0.8.0 divergence now: gate also on the DisableAI/AI-enabled state (the bound-NPC watchdog noted in the PLANCK 0.8.0 compat report overlaps — reuse its detection). 2) Add a physical plausibility check before ANY latch: the head-gap sampler already computes pivot-vs-node Z — refuse to latch a root delta when the instantaneous gap magnitude exceeds a detached-ragdoll-scale bound (e.g. >15u), independent of what the state flags claim. That converts every future PLANCK loosening-condition change from a silent poisoning into a logged refused-latch. 3) Put 'loosening conditions' permanently on the per-update PLANCK checklist.

## [5] [MEDIUM] Collision-comparator registration: NOT a trampoline PPB owns — PPB registers ONE callback into HIGGS's callback LIST via AddCollisionFilterComparisonCallback (PerfSys.cpp:256); HIGGS owns the actual engine trampoline over the game comparator and dispatches registered callbacks with first-non-Continue-wins semantics (PerfSys.cpp:41-48 relies on this). PPB splices its three consumers internally (NpcFinger → HandBox → perf rules) so ordering WITHIN PPB is controlled. Ordering BETWEEN mods = registration order at kPostPostLoad = plugin load order. PLANCK registers its own callback in the same list. Separately, NpcFinger's creation gate exists because the VANILLA fallback for finger-vs-own-ragdoll is COLLIDE (PerfSys.cpp:429-435).
**Scenario**: (a) A third mod (or a PLANCK update) whose callback runs EARLIER returns Collide for a layer-56 pair PPB must Ignore: finger/garment capsule vs the HIGGS hand it must pass through, or box-vs-HIGGS-own-body — PPB's Ignore never executes (first non-Continue already won). Result: garment capsules permanently contact the hand slab (constant FSMP push → tail drags), or the 4 hand boxes grind against HIGGS's palm slab every frame (the judder class the mode-2 anchor was built to kill, reintroduced from outside). No CTD, but a feel regression that looks exactly like a PPB tuning bug. (b) If a HIGGS update changes dispatch semantics (e.g. last-wins or short-circuit removal), the same symptoms appear with no mod added.
**Prevention**: 1) Runtime receipt: the deferred-telemetry flags already prove PPB's Ignore fired (g_logFirstIgnore etc.) — add the inverse: if a finger rig is live and N seconds pass with contact events between its group/part and HIGGS hand parts (Diag's contact listener can see them), log 'comparator preempted — another callback is answering our pairs'. 2) Document that PPB assumes it is the only NON-PLANCK comparator registrant in this load order; on adding any HIGGS-interface mod, re-verify. 3) HIGGS-update checklist: confirm CollisionFilterComparison dispatch is still first-non-Continue-wins and still runs callbacks in registration order.

## [6] [MEDIUM] Writes into HIGGS-OWNED objects: SlabWrite (HandBox.cpp:909-959) writes halfExtents[0..2] directly into the hkpBoxShape of HIGGS's live hand body every frame, via PortHkpBoxShape (radius at 0x20, halfExtents at 0x30, static_asserted). Layout risk is ENGINE-side (Havok 2010.2 hkpBoxShape — frozen with the EXE), NOT HIGGS-version-coupled; the HK_SHAPE_BOX type check makes a HIGGS shape-class change (box → convex/capsule) degrade to a clean no-op. Residual risks: (1) baseline identity is a raw pointer compare (sb.hkBody != hk triggers recapture) — heap address REUSE after HIGGS destroys and recreates a hand body can land the new body at the old address, silently keeping a stale baseline; (2) the shrink-only rule (and the 2× X grow cap) assumes HIGGS keyframes the slab every frame so the broadphase AABB re-derives — if a HIGGS update stops hard-keyframing the slab when idle, a grown X extent stops being picked up (missed contacts, never CTD); (3) rollback: knob back to -1 does NOT restore mid-session (documented — extents recover only on HIGGS's next body recreation).
**Scenario**: For (1): cell transition → HIGGS recreates hand bodies → allocator returns the same address → baseline not recaptured. If the user had meanwhile changed higgs_vr.ini HandCollisionBoxRadius or the beast state flipped, the stale baseline's extents/radius no longer describe the real body: the grow cap (2× stale X) and shrink floors clamp against wrong numbers — slab dialed subtly wrong, symptom is 'my slab dial stopped matching what I set', no log evidence because the recapture line never fires.
**Prevention**: Strengthen the identity key beyond the pointer: also compare the CURRENT extents+radius to the captured baseline at each frame's first sight after any world change — if they differ by more than epsilon while sb.hkBody == hk, treat as recreated-in-place and recapture (one extra compare per hand per frame). Keep the existing 'never dereference after capture' discipline.

## [7] [MEDIUM] HIGGS filter-word CONVENTIONS baked as constants: layer 56 (L_HIGGSCOLLISION) 'only exists under HIGGS' (NpcFingerTest.cpp:217), part field bits 8-12, group in high 16 bits, bit15 ragdoll-adjacency, bit14 collision-off, HIGGS's native parts 3/5 (hand/weapon) and 2/6 (declared-but-dead) hardcoded in both Ignore masks (HandBox.cpp:1399-1404, NpcFingerTest.cpp:1535-1536), part 30 claimed as 'unused band' for fingers, part 4 default for boxes, and the 100 ms kEnableDelayMs mirroring HIGGS's handWeaponCollisionEnableDelay.
